# Layer pipeline

A document is a canvas and an ordered list of steps. Steps run in order, each on the picture the steps before it made, starting from the blank canvas. This file records how images are layered in that picture and why, so the code and the screens can be checked against it.

## The model

A document has a **canvas**: a width and a height in pixels (1 to 65535, at most about 268 million pixels in all, which is Sharp's own limit) and a background, either `transparent` or a colour written `#rrggbb`. The canvas is stored in the pipeline, next to the steps, so it is part of every undo, every document file and every render key. Nothing derives the canvas from an image after the document is made: opening an image makes a document whose canvas is the size of that image, once, and from then on the canvas changes only when the person changes it (`set-canvas`, one undoable edit; File > New document and `document create --width --height` start from a canvas of their own).

Every image in a document is an **image layer** step, drawn on the canvas like any other step. An image layer may be **empty**: it keeps its settings and draws nothing until it has an image (`set-image`, one undoable change that fills it or, with no image, empties it). There is no "canvas layer": the first layer is not special, it has the same settings as the rest, and any layer can be hidden, moved, replaced or deleted without the picture changing size. A new document opened from an image has one layer holding that image. A document may have no layer at all, and then its picture is the blank canvas.

Every step acts on the picture as it stands, starting from the blank canvas. A layer is drawn on it with its own settings, so an effect placed after a layer affects the layer too, and an effect placed before it does not. A step before the first layer works on the blank canvas.

A layer is on top of everything before it in the pipeline. The sidebar lists the steps with the last on top, the way layer panels do, so the row at the top of the list is drawn on top. Moving a row up moves it later in the pipeline and so closer to the viewer.

No step merely "opens" an image for another step to use. A step that needs a second image (boolean, join channel) names an image from the library directly, as a layer does.

## Groups and embedded document layers

A **group** is a step that holds other steps. It has a name, an on/off switch, and a list of steps of its own; it can hold layers, effects, AI steps and other groups, but never an embedded document layer. Moving, switching off or deleting a group does it to everything in it. Switching a group off turns off every step in it, whatever their own switches say; switching it on again gives each step back its own. Whether a group is drawn open or closed in the sidebar is a matter of the screen: it is not saved in the document.

A group changes nothing about the picture. The planner opens it, so the render keys, AI results and thumbnails are exactly those of the same steps without the group. Grouping and ungrouping can therefore be undone and redone freely and never makes anything run again.

An **embedded document layer** is a document inside its parent's pipeline. It starts from a blank canvas of the same size and background as its parent's (it has no canvas of its own to set), the steps in it draw on and act on that picture only, and the result is placed on the parent's canvas like a layer, so it carries the layer settings (`opacity`, `blend`, `fit`, `scale`, `rotation`, `anchor`, `x`, `y`). It holds anything a document holds: steps, groups, other embedded document layers, and document and workflow layers. Resizing the logo inside one resizes the logo and nothing else on the canvas. One with no layer that is on is a picture with nothing in it: it is drawn, and adds nothing visible. It is a copy, not a separate document: it has no id in the library and no edit history of its own, and its changes go on the parent's edit history.

Containers nest to a depth of at most 8, counting groups, embedded document layers and the items document and workflow layers use alike (see below); a pipeline holds at most 1000 steps, a container at most 200, and every id is unique across the pipeline. The limits live in `src/features/pipeline/pipeline-limits.ts` and are checked by the pipeline schema, so the website, the CLI and an imported file all meet the same rule. Where a step may go is decided once, by `placementProblem` in `src/features/pipeline/pipeline-tree.ts`: the container must exist, a step cannot go inside itself, a group cannot hold an embedded document layer at any depth, and the result must stay within the depth limit. Both the `DocumentChange` kinds and the sidebar's drag and drop ask it.

A group and an embedded document layer can be switched into one another (`set-embedded`). A group becomes an embedded document layer with the default placement. An embedded document layer becomes a group by dropping its placement, which is refused when it holds an embedded document layer or when it sits inside a group, since a group cannot hold one. Undo restores the step exactly as it was. Only the planner treats the two differently, in one place (`planSteps`, which opens a group and keeps an embedded document layer that is on as one step). AI steps inside an embedded document layer run on that layer's own picture, one at a time like all AI steps, and their results are stored under keys made from that picture. Their order among the other AI steps is the order of the pipeline: an AI step waits for every one that comes before it, at any depth. A step inside an embedded document layer gets a small picture of that layer at that step, and the layer itself one of its place on the canvas.

## Layer kinds

A layer has a `kind`: `image-layer`, `document-layer` or `workflow-layer`. The registry in `src/features/pipeline/layer-kinds.ts` (the used kinds are in `used-layer-kinds.ts`) owns everything that depends on the kind: its schema, its title, which library images it uses and how they are renamed when a pipeline moves, which document or workflow it uses and how that id is renamed when a document file is opened, whether it takes an image (`withImage`; a document layer does not), why it is not set up, how the sidebar shows it, and how the planner turns it into a drawn image, an empty layer, a layer whose image is gone, or a picture of the item it uses. Nothing else checks for a kind; an unknown kind is refused by the schema. The settings that place a layer (`opacity`, `blend`, `fit`, `scale`, `rotation`, `anchor`, `x`, `y`) are defined once and shared by every kind and by embedded document layers.

## Document layers and workflow layers

A **document layer** draws another of the User's documents as it is now, and a **workflow layer** draws one of the User's workflows as it is now on an image of the layer's own, which fills the workflow's input slot (with none, the workflow draws without an input, like an empty image layer). Both store only the id of what they use and their placement settings, so a change to the used document or workflow changes every picture that uses it. Neither is edited in place: it shows as one row, and its ⋯ menu and options offer **Open**, which goes to that document or workflow, whose changes go on its own edit history (decision 18, edit history). Layers use only the User's own documents and workflows.

The picture is made at the used item's own size, then placed like an image layer (decision 14, canvas and output inside). A document layer draws the document on its own canvas and background. A workflow layer draws the workflow at the size its canvas size mode gives for the layer's image: its own canvas when it is fixed, the image's size when it matches the input. The workflow's output settings are not used there. The planner plans the used item's pipeline as a nested picture (`planUsed` in `src/server/render/plan-pipeline.ts`), so its render keys come from what it applies, and any change to it is a new picture without a revision number. After a document or workflow changes, every document and workflow that draws it, at any depth, is told so its open tabs draw it again (`UsedItems.announcePictureChanged`, the `picture.changed` event).

A group may hold document and workflow layers (decision 15, layers inside a group), and so may an embedded document layer. One limit of 8 levels covers groups, embedded document layers and the items used layers use, all counted together (decision 24, total depth). A layer that would lead back to the document or workflow holding it, at any depth, is refused (decision 13, no circular references); a workflow may hold a workflow layer of another workflow. A document or workflow that a layer uses cannot be deleted: the refusal names the documents and workflows that use it (decision 10, deleting something in use). These rules are in `src/server/services/used-items.ts`, which both front doors reach through the services.

AI steps inside a document layer belong to the used document (decision 20, AI inside a document layer). The parent draws the document's results. A missing one is queued as that document's job, so the result is the document's and is kept with it, and meanwhile the parent's row shows "Waiting for an AI step to run". AI steps inside a workflow layer act on the layer's own image, so they run for the document that holds the layer and their results belong to it (decision 21, AI inside a workflow layer).

**Convert to embedded document layer** puts an embedded document layer holding a copy of the used item's steps, as they are now, in the layer's place, so that this one place can change on its own (decision 11, convert to embedded). A workflow layer's image goes in the copy's input slot. The layer's id, name, switch and placement are kept, and the change is one undoable step (`convert-step`, undone by `restore-layer`). An embedded document layer has no canvas of its own and draws on its parent's, so a used document with a canvas of another size or background looks different after it is converted: what was drawn outside the parent's canvas size is cut off, and what was empty is now the parent's size.

## Create-from

A document can become a new workflow and a workflow a new document, from the whole item or from one group, embedded document layer, document layer or workflow layer in it. The rules are pure functions in `src/features/workflows/create-from.ts`, and each step kind's registry entry says how it is copied into a document and into a workflow (`copy` in `src/features/pipeline/step-kinds.ts`; decision 1, context rules). `CreateFromService` loads the source and saves the new item. The new item's name is the source's, made unique; on the website it can be edited before it is made, and `--name` is optional on the CLI. The new item opens.

**New workflow from document** (`workflow create [<name>] --from-document <id> [--group <stepId>] --images keep|remove|remove-input`) asks what to do with the images (decision 2, workflow from a document): keep them all, remove them all, or remove only the input image, the first image layer's. "All" means every image layer at any depth of groups and embedded document layers, never one inside a document or workflow layer (decision 25, how deep "all images" is). The removed images become the workflow's inputs, its canvas size mode is fixed with the document's canvas, and its output settings are the defaults (decision 3, its canvas and inputs). So going from a document to a workflow and back drops the images the User chose to remove: they are inputs of the workflow, not part of its pipeline.

**New document from workflow** (`document create [<name>] --from-workflow <id> [--group <stepId>] [--width <px> --height <px>]`) makes the input slot a plain image layer holding the input image the workflow shows, the last one added, or an empty one when there is none, and copies every other step as it is (decision 4, document from a workflow). A fixed workflow gives its canvas; one that matches each input image gives the size of the image put in the layer, and with no image the website asks for the size and the CLI needs `--width` and `--height` (decision 5, its canvas).

With `--group`, or from the selected container on the website, the container's steps become the new pipeline's top level, its placement is dropped, and the canvas is the parent's; a new workflow whose steps have no image layer gets an empty one first, as its input slot (decision 6, group as the source; decision 7, what the new pipeline holds). A document layer or workflow layer as the source works on the item it uses, as if that item were opened, and a workflow layer's own image is the input image (decision 26, create-from a used item).

**Insert workflow** (Edit > Insert workflow…, document page only; `document step add <id> --workflow <workflowId> [--source <id>]`) makes an embedded document layer named after the workflow, holding a copy of its steps that is not tied to it, with the chosen image in its input slot or none (decision 8, workflow added as a group). It goes after the selected step, or at the end.

## Workflows

A workflow is the same pipeline a document has (canvas and steps, groups and embedded document layers included), plus the library images it runs on (`inputs`, each at most once) and its output settings. Its **input slot** is the first image layer that is switched on, in pipeline order, at any depth of groups and embedded document layers but never inside a document or workflow layer, whether or not it has an image (`inputSlot` in `src/features/workflows/segments.ts`). A run makes one item per input image, and the image takes the slot's place (a `set-image` change on that item's copy of the pipeline), so an image the slot holds is only what the workflow shows while it is edited. A workflow with no slot cannot run, and nothing runs without an input image. Every other image layer is fixed: it draws the same image in every item, as a logo would, or nothing when it has none.

A workflow's canvas size is saved with it (`canvasSize`): `match-input`, the default for a new workflow, draws each item on a canvas the size of its image and keeps the workflow's background, as a document opened on that image would be; `fixed` draws every item on the workflow's own canvas. It is chosen in the Canvas node's options or with `workflow create|update --canvas-size`, is an undoable change, and a run keeps it in its copy of the workflow.

A run copies, when it starts, its own definition and the current version of every document and workflow its layers use, at any depth, so editing them during a run changes nothing in it (decision 23, runs copy what they use). It is cut into segments at every enabled AI step, at any depth, including inside the documents and workflows its layers use (decision 22, AI at any depth in a run; `src/server/workflows/run-segments.ts`). For each AI step in pipeline order there is a draw segment of everything before it in its own picture (the parent pipeline, or the embedded document layer it is in), drawn as a document is, then the AI step on that picture; a final draw segment draws the whole pipeline. A draw segment finds the result of an earlier AI step under that step's render key, which the run maps to the picture the AI segment made, so an AI step inside an embedded document layer works on that layer's picture and its result is placed with the layer. The final segment is exported with the workflow's output settings, naming the input image as the original whose format "same as original" keeps. A step that cannot be applied (a layer whose image is gone, a tool that is not set up) fails the item with a message.

The Composite tool is not offered in workflows, as in documents: an image layer does what it did. Image layers do not cover generated inputs (`create`, `text`), the `tile` option and the Porter-Duff blend modes of Composite. The `sharp` command keeps Composite for one-off work on files.

On the website a workflow is drawn as a diagram in the middle of the page: the canvas, the input images, the steps in order and the output form the main line, and the steps of a group hang under it as a branch that joins the line again. The layout is worked out from the pipeline (`workflow-graph-layout.ts`), so nothing about it is stored. Selecting a node shows its options in the floating panel, the same panel a document has, with the tabs that apply to a workflow (Tools, Options, Run); a document's panel has none of the workflow's tabs and the other way round. Steps are added from the Tools tab, after the selected node or into a selected group.

A workflow has an Edit history exactly as a document has: each change on the page (a step, a layer, the canvas, the input images, the output settings) is one entry that can be undone and redone from the Run tab, the Edit menu or the keys, and a workflow is held in the client like a document (see the plan's "Client state"). A rename is not an edit.

## Layer settings

A layer has an image, switched on or off like any step, and:

| Setting    | Values                                                                                                                       | Meaning                                                                                                                                                                                                                                                                                          |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `opacity`  | 0 to 100, default 100                                                                                                        | How much of the layer shows through, as a percentage. Multiplies the layer's own transparency.                                                                                                                                                                                                   |
| `blend`    | normal, multiply, screen, overlay, darken, lighten, colour-dodge, colour-burn, hard-light, soft-light, difference, exclusion | How the layer's colours combine with the picture under it.                                                                                                                                                                                                                                       |
| `fit`      | inside, original, contain, cover, stretch                                                                                    | How the layer's image is sized to the canvas before `scale`. `inside` shrinks a larger image to fit and never enlarges, `original` keeps its pixels, `contain` fits it inside the canvas and enlarges if needed, `cover` fills the canvas and crops the rest, `stretch` ignores the proportions. |
| `scale`    | 1 to 1000, default 100                                                                                                       | A percentage applied after `fit`.                                                                                                                                                                                                                                                                |
| `rotation` | -180 to 180, default 0                                                                                                       | Degrees clockwise, about the layer's centre.                                                                                                                                                                                                                                                     |
| `anchor`   | the eight compass points or centre, default centre                                                                           | Which point of the canvas the layer is placed against, and which point of the layer touches it.                                                                                                                                                                                                  |
| `x`, `y`   | whole pixels, default 0                                                                                                      | How far the layer is moved from the anchor, right and down.                                                                                                                                                                                                                                      |

The defaults put an image in the middle of the canvas, shrunk if it is larger, fully opaque.

### Decisions

**The canvas never grows.** A layer larger than the canvas, or moved partly off it, is cut off at the canvas edge. The canvas changes size only when the person changes it, or when a geometry step (resize, extract, rotate) changes the picture, as steps before a layer left it. Hiding, moving or deleting a layer never changes the size of the picture. Changing the canvas does not change the steps: layers keep their settings and land where those settings put them on the new canvas.

**Layers are drawn at full resolution.** The preview is made small only at the end, so placement, scale and rotation do not depend on how big the preview is.

**Compositing keeps transparency.** Transparent and partly transparent pixels in the layer, and in the picture under it, are blended by their alpha, so a PNG with a cut-out shows what is behind it. The canvas shows a checkerboard behind the picture so that transparency can be seen, and exporting to a format that cannot hold transparency (JPEG) flattens the picture onto white.

## Blend on a tool, and the Scale and Opacity tools

A filter or colour step can be blended with the picture as it was before the step. It has the same blend modes as a layer and an opacity from 0 to 100; the default (normal, 100) is the plain step and is not stored. Geometry and AI steps cannot be blended: geometry changes the size of the picture, so there is nothing to compare, and an AI step makes a new picture of its own. A blended step is applied on its own: the engine renders the picture before and after it, fades the result by the opacity, and composites it over the earlier picture with the mode. The blend is part of the step's identity, so it changes the render key.

Scale (Geometry) resizes the picture by a percentage, where Resize is in pixels. Opacity (Colour) makes the whole picture more see-through, multiplying the transparency it already has. Sharp has no operation for either that keeps the order of the steps, so both are applied to pixels with the layers and blended steps. Negate keeps the picture's transparency unless `alpha` is set, so it gives the same result wherever it sits in the pipeline.

## How it is rendered

The planner turns the pipeline into a base and an ordered list of engine steps. The base is the blank canvas, or, after an AI step that has a result, that result (the steps before it are baked into it). The steps are Sharp steps, layers with their image resolved to a file, and embedded document layers, each with its own base (the same canvas) and engine steps, at any depth, which the engine renders to pixels first and then places like a layer. A layer whose image is gone is skipped with a message. The engine applies them in order. Sharp does not run its operations in the order they are listed within one pipeline (it resizes before it composites, for instance), so the engine renders the picture to pixels at every layer and builds the next stage from those pixels. The layer's image is oriented, sized by `fit` and `scale`, rotated, given its opacity, cut to the part that is over the canvas, and composited with its blend mode.

Render keys start from the canvas (`canvas:<width>x<height>:<background>`), so another size or background is another picture. They name an image by its content hash and a layer by its settings, and an embedded document layer by the key-form of everything it applies and its placement (a group has no key of its own), so the same document on another machine, with the same pictures under other ids, finds the same keys. That is what lets a document file bring its AI results with it.

## What changed from the earlier models

The first model let a document hold several "Open image" steps, of which the first was the picture and the rest only made their image available to later steps. The second model made the extra ones layers and kept one locked "Image" step at the bottom. The third model removed that special step: every image is a layer, and the first layer that was switched on set the canvas. The current model gives the document an explicit canvas, so no layer is special. The Composite tool, which did the same job with a list of images in its options, is not offered in documents or workflows; only the `sharp` command keeps it.

Existing documents are migrated in two steps. `20260101000500-layers` made extra image steps layers (or dropped those that only supplied a second image to a boolean or join channel step) and each Composite step a layer per image, with its blend mode and placement. `20260101000600-layers-only` turns the remaining image step into a layer with the default settings, in the same place. Undo history of a migrated document is cleared because the steps change. Document files (`.lemon`) made before layers (bundle version 1) are refused with an explanation, and so are documents and files made before the canvas was explicit: their pipeline has no `canvas`, so it fails validation. There is no conversion for either.

Workflows saved before the pipeline model stored a graph of nodes and edges. They are not converted: they fail to read and must be deleted. The diagram on the workflow page is drawn from the pipeline each time and is not stored.

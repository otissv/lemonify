# Job workers to-do

A list of what needs doing, in build order, not a plan. It fixes the website stalling while images are processed: today the web server runs every job itself, so renders take the helper threads that file reads, uploads and sign-in need, and the CPU and main thread that requests need. Postgres replaces SQLite first (section 1), because separate worker processes write to the database often and at the same time, which SQLite handles worst. Every item is built test first, and `tsc`, `biome check .`, Vitest and the Playwright run pass at the end of each section.

## What was found

| Finding                                                                     | Evidence                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Renders starve the web server's helper threads                              | With 4 renders running, reading a tiny file took 1.2 s; with 8 queued, 2.4 s. Under load the e2e pages stayed on "Loading…" for over 30 s.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| A database write that waits for another process freezes the waiting process | better-sqlite3 waits on the main thread: a write blocked for 2.9 s froze the event loop for 2.95 s. Real CLI commands held the lock for 2 ms at most, so it is rare today, but separate worker processes write often.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Three DAO methods rely on SQLite letting one writer in at a time            | `lockedRow` in the document and workflow DAOs reads `revision`, checks it, then writes `revision + 1`; `finish` in the job DAO reads `cancel_requested`, then writes the outcome. Under Postgres's default isolation two transactions both pass the read: an undo (`moveCursor`) and an edit in another tab both save the same revision and the history no longer matches the pipeline; two edits at once (`applyChange`) end in a raw primary key error on `history_entries` instead of the stale document conflict; a cancel between the read and the write is missed, so a cancelled run queues its next segments. `claim` and `requestCancel` are single conditional updates and are already safe. |
| `e2e/api.spec.ts:265` fails on a repeat or retry                            | It always names its workflow "Api run": "A workflow with this name already exists."                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

What already works across processes and is reused: the job queue is in the database, a job is claimed with one conditional update, jobs of a process that is gone are failed (`Scheduler.reapOrphans`), and a cancel is read from the database (`cancelRequested`).

## Decisions

| #   | Short name        | Decided                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --- | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Worker processes  | The web server runs no jobs. It starts a fixed pool of worker processes with `child_process.fork`, restarts one that stops, and stops them all when it stops.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| 2   | Pool shape        | One CPU worker process per CPU slot (`LEMONIFY_CPU_WORKERS`, at most 4 by default), each running one job at a time; one GPU worker process that keeps the AI models loaded and batches AI jobs.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| 3   | Work per image    | Work is shared out per job (one per input image, or per segment of a run with AI steps), not per workflow, so one workflow spreads over every worker and the 50% rule (`LEMONIFY_GROUP_SHARE`) keeps runs fair.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| 4   | Live updates      | Every process that runs the core (the web server, each worker, each CLI command) sends what changed to the web server through one local socket in the data folder, readable only by the user who runs Lemonify. The web server tells the open tabs through `RealtimeHub`. When no web server is running there are no tabs, and the change is not sent.                                                                                                                                                                                                                                                                                                                                                                                        |
| 5   | Database waits    | No process waits for the database on its main thread: the `pg` driver is asynchronous, so a wait for a lock is a pending promise, not a frozen event loop. No retry layer is built. Every connection sets `lock_timeout` and `statement_timeout`, so a wait ends with a clear error instead of hanging.                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 6   | CLI               | A CLI command does its jobs in its own process (`scripts/images/job-workers.ts`) only when no web server is running, so it still works on its own. When a web server is running (its socket answers), the command queues its jobs and the server's worker pool does them; the command waits for the results and prints them as it does now. However many agents run the CLI, the pool's worker count and the 50% rule (`LEMONIFY_GROUP_SHARE`) hold.                                                                                                                                                                                                                                                                                          |
| 7   | CLI and website   | A change made with the CLI reaches open tabs like one made on the website, because the core announces it through the channel of decision 4 (live updates), whichever process it runs in.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 8   | GPU worker start  | The GPU worker starts only when an AI job is queued, which needs an AI tool set up, and stops after it has been idle for a while, so no models are loaded and no GPU memory is held when no document or workflow uses AI.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 9   | Postgres          | Postgres replaces SQLite for Lemonify's tables and Better Auth's. Lemonify is a web server on one machine, so Postgres runs beside it (or as a managed database), and the CLI reaches it through the same settings. Knex uses the `pg` client with a pool. The SQLite DAOs, `better-sqlite3` and `@types/better-sqlite3` are removed, with no SQLite fallback; `LEMONIFY_DATABASE` and `databaseFile` go, and the required `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DATABASE` and `POSTGRES_SCHEMA` take their place, read from the environment and from `.env` (the environment wins), the same settings `compose.yaml` reads. `LEMONIFY_DATABASE_POOL_SIZE` (default 10) sets each process's pool. |
| 10  | No data migration | Nothing is in production and there are no users, so no data is copied from SQLite. The 12 SQLite migrations are replaced by one starting migration that creates today's schema, and the tests of the data rewrites in those migrations go with them because the rewrites no longer exist. `.data/lemonify.sqlite` is deleted once.                                                                                                                                                                                                                                                                                                                                                                                                            |
| 11  | Column types      | JSON columns are `jsonb` and still validated by their Zod schemas on read; flags (`cancel_requested`) are `boolean`; times are `timestamptz`, turned into UTC ISO strings in the DAOs, so the DAO interfaces and services do not change. Better Auth's tables are what its `generate` command makes for Postgres.                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 12  | Row locks         | `lockedRow` (document and workflow DAOs) and the read in `finish` (job DAO) take the row with `FOR UPDATE`, so a second transaction on the same row waits for the first and then sees its result: a stale revision becomes the stale document or workflow conflict, and a cancel is never missed.                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 13  | Local Postgres    | Development runs Postgres 18 in a container from `compose.yaml` in the repository, bound to `127.0.0.1`, with its data in a named volume. Production uses the same major version.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 14  | Test databases    | DAO tests and the e2e run use a real Postgres, because PGlite has one connection and cannot run the two-transaction tests that decision 12 (row locks) needs. Each test run migrates one template database (`lemonify_test_<run>`, in Vitest's global setup), and every test that needs a database gets its own copy (`CREATE DATABASE … TEMPLATE`, about 25 ms) and drops it at the end, so tests stay isolated and files run in parallel; the run drops whatever is left when it ends. Vitest points `POSTGRES_DATABASE` at a database that does not exist, so a test that forgets to make its own fails instead of changing the database in `.env`. Services keep their in-memory DAO fakes and need no database.                          |

## 1. Postgres (decisions 5, database waits; 9, Postgres; 10, no data migration; 11, column types; 12, row locks; 13, local Postgres; 14, test databases)

- [x] `compose.yaml` with Postgres 18 (decision 13, local Postgres) and a README section on starting it and on the `POSTGRES_` settings in `.env`.
- [x] Config: the `POSTGRES_` settings are required and validated by the config schema, with a message naming the one missing; `.env` is read by `src/server/config/environment.ts`; `LEMONIFY_DATABASE` and `databaseFile` are removed; config tests say so.
- [x] `src/server/database/connection.ts` opens Knex with the `pg` client and a pool, sets `lock_timeout` and `statement_timeout` on each connection (decision 5, database waits), and reads `timestamptz` and `bigint` the way the DAOs expect. `applyPragmas` is removed.
- [x] One starting migration with today's schema, constraints and indexes (decision 10, no data migration; decision 11, column types), including Better Auth's Postgres tables; the 12 SQLite migrations and `document-order-migration.test.ts`, `layers-migration.test.ts`, `layers-only-migration.test.ts`, `open-image-steps-migration.test.ts` and `workflow-canvas-size-migration.test.ts` are deleted; `migrate.test.ts` checks the Postgres schema and that Better Auth has nothing left to create.
- [x] The DAOs move from `src/server/dao/sqlite/` to `src/server/dao/postgres/` as Postgres classes: flags as booleans, times as ISO strings. `jsonb` columns are written as JSON text and read back as text (the pool's own type parser), so each DAO still parses and validates them and reports bad rows as unreadable. The source insert is `on conflict do nothing`, so two uploads of the same picture at once end with one row. The contract tests in `src/server/dao/contract/` pass against them unchanged.
- [x] Row locks (decision 12, row locks), each with a test (`src/server/dao/postgres/row-locks.test.ts`; all five fail without `FOR UPDATE`) that runs two transactions at once: an undo and an edit of the same revision leave one saved and one conflict, with the history matching the pipeline; two edits of the same revision give one stale document conflict, not a database error; the same for workflows; a cancel requested while `finish` runs queues no next segments.
- [x] Better Auth uses a `pg` pool on the same settings; the auth gateway tests pass.
- [x] Test databases (decision 14, test databases): `createTestDatabase` gives each caller its own database from the migrated template and drops it on `close`; `createTestApp` and the CLI flow tests use one each; `insertTestUser` writes Better Auth's Postgres row.
- [x] The e2e server uses its own database (`lemonify_e2e`), recreated from empty at the start of each run as `e2e/.data` is; `workflow-cli.spec.ts` gets a database of its own beside its data folder.
- [x] The CLI connects with the same settings and, when Postgres cannot be reached, fails with an `unavailable` error (exit code 7, HTTP 503) that names the host and port and how to start the local server.
- [x] `pg` added; `better-sqlite3` and `@types/better-sqlite3` removed.
- [x] `.data/lemonify.sqlite` deleted once, with the sources, results and render cache that belonged to it.

## 3. The channel from the core to the web server (decisions 4, live updates; 7, CLI and website)

- [x] A message schema (zod) for what a process sends (`src/server/channel/channel-message.ts`): one change, the person it is for and the same realtime event the tabs get, one JSON line each (section 6 adds a `queued` message naming pools). Messages that fail the schema are logged and dropped. Worker ready and stopping messages are not on this socket: the pool hears them from its own children over `fork`'s IPC channel (section 5). Job progress is not either: it is saved to the database, which tabs already read, so the channel carries only changes and, from section 6, which pools jobs were queued for.
- [x] The web server listens on a local socket in the data folder (`run/lemonify.sock`), in a folder only its user can enter and owns, the socket itself 0600, removed when the server stops, a stale one from a killed server replaced at start, and a second web server on the same data folder refused (`src/server/channel/channel-server.ts`). A data folder too deep for a socket path is refused at configuration.
- [x] A `ChangePublisher` for every process that is not the web server (workers and the CLI, `AppRole.Process`, the default): it writes to the socket without waiting, does nothing when no server is listening, bounds what waits to be written, reconnects after the server restarts, and writes what is waiting when the command ends (`src/server/channel/channel-client.ts`).
- [x] The receiver in the web server passes events to `RealtimeHub` (`src/server/http/runtime.ts`).
- [x] Tests: an event sent from another process reaches the owner's open tabs; an edit made with the CLI reaches them; several CLI processes at once all reach them; a bad message changes nothing; a CLI command with no server running finishes as fast as before (`src/server/channel/*.test.ts`, `scripts/images/live-updates-flow.test.ts`); and through the real web server, a document made and renamed with the CLI shows in an open tab without a reload (`e2e/realtime.spec.ts`).

## 4. The worker process (decisions 2, pool shape; 3, work per image)

- [x] A worker entry (`src/server/worker/main.ts`, forked with the pool as its one argument) and its composition (`src/server/worker/worker.ts`): the services a job needs, built by the same job core the web server and CLI use (`src/server/compose/job-core.ts`), without the web server, the realtime server or auth, and a scheduler for one pool with one job at a time (the GPU worker batches AI jobs inside its one). It stops on SIGTERM, SIGINT or when the process that started it goes away, letting the running job finish.
- [x] Its helper thread pool is sized for its work in the `fork` environment (`workerEnvironment` sets `UV_THREADPOOL_SIZE`, read only at start), and a CPU worker's Sharp threads are the machine's cores shared between the CPU workers (`src/server/worker/worker-environment.ts`).
- [x] Its database pool is two connections (`WORKER_DATABASE_POOL_SIZE`), so the total of every process's pool stays inside Postgres's connection limit.
- [x] Tests: a worker takes a job from the queue, runs it, records its result and finishes it; a CPU worker runs one job at a time and leaves GPU jobs alone; two workers never take the same job; a cancel stops a job in the GPU worker and tells the AI tool to stop; closing lets the running job finish and takes no other; what a job changes reaches the owner's open tabs over the channel (section 3). Job progress is saved to the database, which tabs read, as section 3 decided. The entry is tested as a forked process: it runs a job, stops cleanly on SIGTERM and when its parent goes away, and refuses an unknown pool (`src/server/worker/*.test.ts`).

## 5. The pool in the web server (decisions 1, worker processes; 2, pool shape)

- [x] A supervisor that starts the CPU workers, starts the GPU worker when an AI job is queued and stops it after it has been idle (decision 8, GPU worker start), restarts a worker that stops with a growing delay, and stops them all, letting running jobs finish, when the server stops. (`src/server/worker/supervisor.ts`, forking with `src/server/worker/fork-worker.ts`: restarts wait 1 s, doubling to 30 s, and back to 1 s once a worker has stayed up a minute; the queue is checked for AI jobs every 2 s, which also catches ones other processes queue, and the GPU worker stops after 5 minutes with none; a worker still busy 2 minutes after the server asked it to stop is ended and its job failed. Workers say `ready` and `stopping` over `fork`'s channel and take `wake` from it (`src/server/worker/worker-messages.ts`). However the server process ends, its workers see the channel close, finish their job and exit.)
- [x] The web server no longer starts its own scheduler; a job queued on the website wakes a free worker. (`AppRole.WebServer` gives the scheduler no slots and starts the pool; `JobService` passes the queued jobs to `onQueued`, and the pool wakes the ready workers of their pools.)
- [x] A job left running by a worker that stopped is failed with the existing orphan message (`reapOrphans`), and the owner's tabs are told. (At once when the worker exits, and at the pool's start; a workflow run's job closes the run, which sends `workflows.changed`; a document's job is read as failed by the tab following it.)
- [x] `LEMONIFY_CPU_WORKERS` and `LEMONIFY_GPU_WORKERS` now count processes; config tests and messages say so. (A bad value says "it is how many worker processes the web server starts". A worker is started with the web server's database, data folder and worker counts, whatever its environment says.)
- [x] Tests: the pool starts the right number of workers, restarts one that is killed, and stops cleanly; a killed worker's job is failed and the next job runs. (`supervisor.test.ts` with stand-in processes and fake timers; `worker-pool.test.ts` with real forked workers; `composition.test.ts` for the web server's app; `worker-process.test.ts` for the messages.)
- [x] The render test in `e2e/responsiveness.spec.ts` passes; its `test.fail` mark is removed.

## 6. The CLI (decisions 6, CLI; 7, CLI and website)

- [x] A CLI command that queues jobs checks whether a web server is running (its socket answers). Found on the way:

- A worker that had closed everything was seen, under load, to stay alive after the process that started it went away; `main.ts` now ends the process once it has closed.
- Workers run 10 steps of niceness below the web server (`workerPriority`), since the CPU workers share every core between them and a long render otherwise took the server's CPU.
- Tests that start processes are named `*.process.test.ts` and run as their own Vitest group after the rest, so the processes they start do not starve tests with short timeouts.

## Weaknesses to return to

- `e2e/responsiveness.spec.ts` runs as its own Playwright project that depends on every other spec (`playwright.config.ts`), so its timings are not disturbed by other specs' renders. When any other spec fails, Playwright skips it instead of running it, so a run with an unrelated failure says nothing about responsiveness. Revisit once the worker pool (section 5) keeps renders off the web server, when it may be able to run beside the others.

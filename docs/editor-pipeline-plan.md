# Editor pipeline plan

Status: everything in this plan is built: the editor's five steps, the Documents rewrite and the server architecture (all five slices of "Build order for the rewrite"). "Built" says where each piece lives; the sections after it are the specification it follows, with the settled deviations recorded under "Build decisions". Terms are defined in `docs/glossary.md` and used throughout. What could not be run in the sandbox is listed under "Not checked in the sandbox". Written so a new session can pick it up without the conversation that produced it.

**Editor details.**

- The preview is requested 120 ms after a change. Typing in an options form becomes one History entry after 400 ms, or at once when a field loses focus or the form closes (`use-step-draft.ts`).
- The page has no header. A menu bar at the top of the floating panel holds File (Open image, Open library image, Import document, Export, Close document), Edit (Undo, Redo, Insert image, Replace image, Show original, a view toggle with no entry), View (the Tools, Options, Export and Results panels, the sidebar) and Account (the User's name, Sign out). Pages with no Document get a panel holding only the menu. Ctrl/Cmd+Z and Ctrl/Cmd+Shift+Z or Y work from the keyboard, and notices appear for a failed change, a revision conflict or a failed Render.
- Each Document in the sidebar collapses and expands; its Steps are listed in order with a thumbnail, a status line (options set, what a Step still needs, "Out of date", "Rendering 40%" with Cancel, or why it failed), an on/off switch, move buttons, delete and drag to reorder.
- The Tools panel has tabs Tools, Options and Export. Tools is a search box and the groups AI, Geometry, Filters and Colour (41 tools; the Output group is left to Export). An AI Step has Run, not Apply.
- The form fields (`src/features/workflows/fields/`) are a colour control (picker, any CSS colour as text, opacity), a matrix grid (affine 2 × 2, recomb 3 × 3 or 4 × 4, a convolve kernel as wide and high as the Step's width and height), an image chooser over the User's Sources for the boolean operand and join channel images, and a layers editor for composite.
- Export queues an export Job and downloads the Result from `/api/results/<id>`. It is refused, with the reason in plain words, while an AI Step has no Result or a Step is not set up.
- The Results panel lists a Document's Results with download, delete and "clear unused"; the workflow page lists a run's progress, cancel, delete and each image's download.

## Server architecture

Built. Before it there was no queue: a preview rendered as soon as it was asked for, and `UpscaleJobs` held running upscales in memory, so one busy Document or workflow could crowd out the rest and nothing survived a restart. The sections after this one (data model, History patches, interfaces, errors, CLI commands, configuration, testing) are the specification the slices followed. Terms: `docs/glossary.md`.

**Layers.** Each layer talks only to the one below it, through an interface.

| Layer    | Does                                                                                                                                                | Talks to                      |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| API      | Server functions and routes. After the middleware chain has run, each handler only calls one service and shapes the response. No checks of its own. | Services only                 |
| Services | All the rules: ownership, Pipeline edits, History, planning a render, queueing, running a workflow. No SQL, no Sharp calls.                         | DAOs and tools, as interfaces |
| Tools    | Do the image work: Sharp, the AI tools (Upscayl first), the Source folder, the render cache, the Results folder.                                    | The disk, the GPU             |
| DAOs     | One interface per kind of data: `DocumentDao`, `SourceDao`, `JobDao`, `WorkflowDao`. Each method is a whole operation.                              | The database                  |

- **Why services sit in the middle:** a service never imports Knex, Sharp or a driver, only the DAO and tool interfaces, which are defined next to the services. Changing the database means writing new DAO classes; the services, API and tests of the rules do not change.
- **Several databases:** the SQLite DAOs are the first implementation. A second set (for example Postgres) implements the same interfaces, and a config value picks the set once at startup, in one composition file that builds every service. No service reads that config.
- **Tests:** services are tested against in-memory fakes of the DAOs and tools, so the rules are checked without a database, a GPU or Sharp.
- **Better Auth:** it owns its own tables and has its own database adapter, so it sits beside the DAOs, not behind them. Changing database also means changing its adapter, one line in its config.
- **No singletons:** every service, DAO and tool is an object built in the composition file (`src/server/composition.ts`) and passed in; the composition also builds the `Scheduler` and the daily cleanup (`runMaintenance`).

**Middleware.** Everything that applies to many endpoints is middleware (TanStack Start `createMiddleware`), run before the handler, so handlers never repeat it and an endpoint cannot forget it. Routes and server functions opt in by listing a chain; the ones that need a User use the full chain.

| Middleware   | Does                                                                                                                                                                         | Adds to context                  |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| Session      | Asks Better Auth who is calling; rejects the request with 401 when nobody is signed in. This is the only place the app talks to Better Auth for a request.                   | `actor` (the User)               |
| CSRF         | Checks the origin and token on every request that changes data.                                                                                                              |                                  |
| Rate limit   | Limits requests per User and per address; stricter on upload and on queueing a job.                                                                                          |                                  |
| Sanitise     | Validates the body, search params and path params with each endpoint's Zod schema, so handlers read `context.body` and `context.searchParams`, as the project rules require. | `body`, `searchParams`, `params` |
| Upload guard | On upload routes only: checks the content type and magic number, the size limit, and gives the upload a random stored name.                                                  | the checked upload               |
| Errors       | Wraps the chain: turns every thrown error into a plain-words response (`errorResponse()`), logs it with context, and never exposes a stack trace in production.              |                                  |
| Request log  | Logs method, route, User id and duration for monitoring.                                                                                                                     |                                  |

- **Who may touch which Document is not middleware.** It depends on the data, and jobs run with no request at all. The middleware only establishes the `actor`; every service method takes the `actor` and checks ownership itself, so the rule holds for a request, a queued job and a workflow run alike, and a handler cannot skip it.
- **Why the split:** middleware answers "who are you and is this request well formed", which needs no data; services answer "may you do this to this thing", which does.

**The CLI.** Everything the website does can also be done from the `lemonify` CLI, so agents, scripts and people in a terminal use the same system. A workflow run is started and followed from the CLI, and the website is one more caller of the same services. The CLI and the website API are two front doors onto the services, never separate implementations.

The CLI always runs on the machine that holds the data. On a deployed server, a person or agent signs in to that machine and runs it there; on a developer's machine, that machine is the server. There is no CLI-to-server network connection, so there are no API keys and no remote client.

| Topic              | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| How it runs        | A CLI command builds the same services from the composition file as the server does and calls them in its own process. It needs no running server and no credential: whoever has a shell on the machine can already read the database file.                                                                                                                                                                                                                                                      |
| Ownership          | The CLI acts as an existing User, the `actor` every service checks. `--user <name>` picks one who signed up on the website; with no `--user` it uses the only User, and with no Users at all it creates one local User on first use (through Better Auth's sign-up with a random password that is never stored or shown, so no one can sign in as that User on the website). With several Users and no `--user` it refuses. The CLI has no account of its own and is not a way around ownership. |
| Shared queue       | The queue is the `jobs` table, so the server and any CLI process on the machine feed and drain the same queue. A worker claims a Job with one atomic update, so two processes never take the same Job, and fairness is worked out from the table, not from one process's memory.                                                                                                                                                                                                                 |
| Concurrent writers | SQLite runs in WAL mode so the server and a CLI process can use the database together; writes are short transactions through the DAOs.                                                                                                                                                                                                                                                                                                                                                           |
| Engine commands    | The existing stateless commands (`lemonify sharp`, `upscale`, and the rest, each a JSON job in and JSON out) stay as they are. They are the tools layer: workers run Sharp and the AI tools through them, and agents can still call them directly on any image with no database or sign-in.                                                                                                                                                                                                      |
| Output             | Every command prints JSON and reports errors as JSON, so agents can parse it; `--follow` streams a Job's progress.                                                                                                                                                                                                                                                                                                                                                                               |

**Jobs and workers.** All slow work is a Job, and a Job is a row in the database, so it survives a restart and can be listed, cancelled and shown with progress.

| Topic        | Decision                                                                                                                                                                                                                                                                               |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Job kinds    | Render (a preview or thumbnails), an AI Step, export, and a workflow run, which is split into one Job per Source.                                                                                                                                                                      |
| Worker pools | A CPU pool for Sharp work and a GPU pool for AI tools, each with its own limit (the GPU pool is 1 per GPU). A Job waits for a free slot in its own pool, so a long AI Step never blocks a preview.                                                                                     |
| Fairness     | Waiting Jobs are grouped by what they belong to: a Document, or a workflow run. The scheduler serves each group in turn, and no group may hold more than a set share of a pool's slots, so one Document or one workflow cannot hog it. A per-User limit on waiting Jobs stops a flood. |
| Priority     | Interactive work (a preview the User is looking at) goes before background work (a workflow run), within the fairness rule.                                                                                                                                                            |
| Latest wins  | A new preview for a Document replaces its waiting one, and cancels its running one, so the queue never fills with stale previews. `RenderService` cancels the older-revision Jobs, and a handler that finds the Document's revision changed throws `StaleJobError`.                    |
| Cancel       | A waiting Job is dropped; a running one is stopped through its process group. A Job asked to cancel ends as `cancelled` even if it finished meanwhile, keeps any Result it made, and queues no following Jobs. Progress is read by polling.                                            |
| Restart      | Jobs found running at startup are marked failed with a plain-words reason, and waiting Jobs continue. Renders are a cache, so a lost Render is simply queued again.                                                                                                                    |

**Batching.** A Pipeline is cut into segments at each AI Step.

- **Sharp segments:** the consecutive Sharp Steps between two AI Steps run as one Sharp pipeline (one decode, all the operations, one encode), as `planPipeline` already does for one render. A render Job covers a whole segment, never one Step at a time.
- **AI segments:** images in a workflow run that go through the same AI tool with the same model and settings (the tool's `batchKey`) are run together when its engine takes a batch (Upscayl's CLI takes a folder). The model loads once instead of once per image, and progress is still reported per image. A batch has a size cap so a failed or cancelled batch loses little. A GPU worker waits a 300 ms batch window after claiming an AI Job for companions to arrive before it starts.
- **Order:** a Document's segments run in order, because each needs the result of the one before it. Different Documents, and different Sources in a workflow run, run independently.

**Settled when building:** the pool sizes, the group share and the Upscayl batch cap are configuration with the defaults in "Configuration"; they are tuned against real use, not designed.

## Data model

One SQLite file, `.data/lemonify.sqlite`, in WAL mode, changed only through Knex migrations. Better Auth's own tables (`user`, `session`, `account`, `verification`) are generated into the same migration history; the `owner_id` columns below refer to its `user.id`. Ids are UUIDs. Times are UTC ISO strings. Each JSON column is validated by the Zod schema that is the source of truth for its shape, and a row that fails its schema is reported as unreadable, never converted.

| Table               | Columns                                                                                                                                                                                                               | Notes                                                                                                                                                                                                                          |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `sources`           | `id`, `owner_id`, `content_hash`, `file_name`, `media_type`, `bytes`, `width`, `height`, `created_at`                                                                                                                 | Unique on (`owner_id`, `content_hash`), so one User uploading the same image twice gets the same Source. The bytes are one file, `.data/sources/<content_hash>`, shared by every row with that hash. Never updated.            |
| `documents`         | `id`, `owner_id`, `source_id`, `name`, `pipeline` (JSON), `revision`, `history_cursor`, `created_at`, `updated_at`                                                                                                    | `pipeline` is the current Pipeline and is the truth; History is only for undo and redo. `revision` rises by one on every change and is how two tabs avoid overwriting each other (see "History patches").                      |
| `document_operands` | `document_id`, `source_id`                                                                                                                                                                                            | Every Source a Step uses as a second image (boolean, join channel, composite layers). Kept in step with `pipeline` by `DocumentDao`, in the same transaction, so a Source in use can be found without reading every Pipeline.  |
| `history_entries`   | `document_id`, `position`, `patch` (JSON), `created_at`                                                                                                                                                               | Primary key (`document_id`, `position`). Holds at most 100 rows per Document; the oldest is deleted first. Deleted with its Document.                                                                                          |
| `workflows`         | `id`, `owner_id`, `name`, `graph` (JSON: the existing Workflow nodes and edges, with its Input and Output settings), `revision`, `created_at`, `updated_at`                                                           | Replaces `.data/workflows/*.json`. An Input node lists Source ids, not paths.                                                                                                                                                  |
| `workflow_runs`     | `id`, `workflow_id`, `owner_id`, `graph` (JSON), `state`, `created_at`, `finished_at`                                                                                                                                 | One row per start of a Workflow. `state` is derived from its Jobs and stored so it can be listed. A run keeps a copy of the `graph` it started with (`graph` column), so editing the Workflow mid-run does not change the run. |
| `jobs`              | `id`, `kind`, `owner_id`, `pool`, `priority`, `group_key`, `document_id`, `workflow_run_id`, `state`, `progress`, `payload` (JSON), `result` (JSON), `error`, `claimed_by`, `created_at`, `started_at`, `finished_at` | `group_key` is the Document id or the workflow run id, whichever the Job belongs to, and is what fairness groups by. `claimed_by` is the process (server or CLI) running it. `payload` and `result` are validated per `kind`.  |

**Sources and the disk.** A Source row is the User's claim on the bytes. The file is written by `SourceStore` to a temporary name, checked, then renamed to `.data/sources/<content_hash>` (renaming is atomic, and an existing file with that hash is kept). Deleting a Source is refused while a Document uses it as its Source or as an operand (`document_operands`); otherwise the row is deleted, and the file is removed after the transaction commits only when no other row has the same `content_hash`. Deleting a Document removes its History and operands, never its Source.

The `results` table is described under "AI tools and Results". Job rows never own an image.

**Job states.**

| State       | Meaning                                                                                                                                                       | Leaves to                                   |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| `waiting`   | Queued; no worker has it.                                                                                                                                     | `running` (a worker claims it), `cancelled` |
| `running`   | A worker holds it; `claimed_by` says which process, `progress` is 0 to 1.                                                                                     | `done`, `failed`, `cancelled`               |
| `done`      | Finished; `result` says what it made (a Render key for a preview or thumbnail, a Result id for everything else).                                              | Nothing.                                    |
| `failed`    | Stopped with a plain-words `error`. A Job found `running` at startup becomes `failed` with a reason that says the server restarted.                           | Nothing; a new Job is queued to try again.  |
| `cancelled` | Dropped while waiting, or stopped while running through its process group; a running Job asked to cancel ends here even if it finished, with its Result kept. | Nothing.                                    |

A worker claims a Job with one atomic update (`waiting` to `running`, setting `claimed_by`, only where the state is still `waiting`), so two processes never take the same Job. Finished Jobs are kept for 30 days and then deleted. Only the row goes: the image it made is a Render (cache) or a Result (kept) and follows its own rules, so deleting a Job loses no image. A workflow run is not swept: it is kept until the User deletes it (`workflow run delete`), and its Results go with it.

**Job kinds and payloads.**

| Kind        | Pool                    | Payload                                                                              | Result                                      |
| ----------- | ----------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------- |
| `preview`   | CPU                     | `documentId`, `revision`, display width                                              | Render key of the preview                   |
| `thumbnail` | CPU                     | `documentId`, `revision`, the Step ids to show                                       | One Render key per Step                     |
| `ai-step`   | GPU                     | `documentId`, `revision`, `stepId`, `toolId`                                         | Result id of the AI Step's image            |
| `export`    | CPU                     | `documentId`, `revision`, export settings                                            | Result id of the full-size image to deliver |
| `run-item`  | CPU or GPU, per segment | `workflowRunId`, one Source id, the segment index, the previous segment's work image | Result ids (empty until the last segment)   |

A `revision` in the payload pins the Job to one state of the Document, so a Job never renders a Pipeline the User has already moved on from; if the Document's revision is newer when the Job starts, the Job is cancelled as stale, which is how "latest wins" is enforced.

## History patches

Each change to a Pipeline is one `history_entries` row holding a reversible patch: the change and what is needed to undo it. A patch is a Zod discriminated union on `type`.

| `type`        | Forward data                      | Undo data                            |
| ------------- | --------------------------------- | ------------------------------------ |
| `add-step`    | `step`, `index`                   | none (undo removes `step.id`)        |
| `remove-step` | `stepId`                          | the removed `step` and its `index`   |
| `move-step`   | `stepId`, `to`                    | `from`                               |
| `set-options` | `stepId`, `options` or `settings` | the previous `options` or `settings` |
| `set-enabled` | `stepId`, `enabled`               | the previous `enabled`               |

`history_cursor` on the Document counts the entries that are currently applied. Undo applies the undo data of the entry at `cursor - 1` and lowers the cursor; redo applies the forward data of the entry at `cursor` and raises it. A new change deletes the entries at and above the cursor (the undone ones), inserts one at the cursor, and raises it; when there are more than 100 entries the oldest is deleted. Because `documents.pipeline` always holds the current state, dropping old entries loses nothing but the ability to undo that far. Every change, undo and redo is one transaction that writes `pipeline`, `document_operands`, the entry, the cursor and `revision` together.

**Revisions.** Every change request carries the `revision` the client last saw. If it differs from the stored one the service refuses with a conflict, and the client reloads the Document and shows what changed; nothing is merged silently. This is what makes two tabs and two devices safe.

## AI tools and Results

**AI tools.** An AI tool is a Step that runs a model, on the GPU by default. Upscale is the first. Others are expected after this plan is built (background removal, sky selection, portrait focus and similar small image-processing models), so the plan makes room for them without designing them. A Step is `{ kind: 'sharp', op, options }` or `{ kind: 'ai', tool, settings }`, and `tool` names an entry in the AI tool registry.

| Registry entry | Holds                                                                                                                                                |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`, `label`  | The tool's id (stored in Steps) and its name in the Tools panel's AI group.                                                                          |
| `settings`     | The Zod schema for the tool's settings. The Pipeline schema, the options form and the CLI all derive from it, so a tool's settings are written once. |
| `engine`       | Which `AiEngine` adapter runs it, and its models.                                                                                                    |
| `pool`         | `gpu` unless the tool says otherwise.                                                                                                                |
| `batchKey`     | A function of the settings that says which images can run in one batch, so batching works the same for every tool.                                   |
| `output`       | `image` today. Reserved for tools whose output is not a finished image (a mask).                                                                     |

Adding a tool means one registry entry and one engine adapter. Services, the queue, the cache, the DAOs, the middleware, History, the routes and the database do not change, because Step settings are JSON validated by the registry's schema, and the Tools panel, the options form and the CLI list the registry. How a mask feeds a later Step (sky selection, portrait focus) is settled when the first such tool is designed; `output` is the room left for it.

**Renders and Results.** Two kinds of stored image, with different rules, so the 2 GB limit can never cost the User work:

| Kind   | What it is                                                                                                        | Stored in                  | Removed                                                                                                       |
| ------ | ----------------------------------------------------------------------------------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Render | A preview, a thumbnail, or a Sharp intermediate. Cheap to recompute.                                              | `.data/render-cache/<key>` | By the cache's own 2 GB least-recently-used rule, at any time. Rebuilt on demand with no User action.         |
| Result | An image that cost real work or that the User asked for: an AI Step's output, an Export, a workflow run's output. | `.data/results/<key>`      | Only when the User deletes it, deletes its Document or workflow run, or clears unused Results. Never evicted. |

The `results` table holds `id`, `owner_id`, `kind` (`ai-step`, `export`, `run-item`), `key` (the same content hash used for Render keys), `document_id`, `step_id`, `workflow_run_id` (each nullable), `file_name`, `media_type`, `bytes` and `created_at`. As with Sources, one file serves every row with the same `key`, and the file is removed after the transaction commits only when no row is left for that key.

- **Out of date** for an AI Step now means "no Result exists for the key of this Step", as it meant "no Render" before; the planner starts from the last AI Step that has a Result.
- **Superseded Results stay.** Changing a Step's settings makes a new key and leaves the old Result, because undo can bring it back. `RenderService.clearUnusedResults(actor, documentId)` deletes the AI Step Results the Document's current Pipeline does not use (exports are deliveries and are never touched); undo then needs a rerun for those.
- **Deleting a Document** deletes its Results after the User confirms, and the confirmation says how many and how large they are. The Source is never deleted.
- **Quota.** `MAX_RESULT_BYTES_PER_USER` limits what a User keeps. Queueing a Job that would exceed it raises `LimitError` with a message that points at clearing unused Results. This replaces the cache cap as the storage limit for work the User cares about.
- **Export** writes a Result. The web downloads it and the CLI copies it to `--out`. The Result stays after either, so a download that fails can be repeated.

## Errors

Services throw custom error classes; the Errors middleware and the CLI each turn them into their own output, so a rule is written once.

| Error               | Raised when                                                     | Web status              | CLI exit code |
| ------------------- | --------------------------------------------------------------- | ----------------------- | ------------- |
| `ValidationError`   | An input fails its schema, or an upload fails the upload guard. | 422                     | 2             |
| `NotFoundError`     | The thing does not exist, **or belongs to another User**.       | 404                     | 3             |
| `ConflictError`     | The revision differs, or a Source is still in use.              | 409                     | 4             |
| `LimitError`        | A rate, size, quota or waiting-Jobs limit is reached.           | 429                     | 5             |
| `UnauthorizedError` | Nobody is signed in (Session middleware only).                  | 401                     | not used      |
| `JobFailedError`    | A Job the caller waited for ended `failed` or `cancelled`.      | 200 with the failed Job | 6             |

A User asking for another User's Document or Source gets `NotFoundError`, the same as for one that does not exist, so ownership never leaks what exists. Every message is plain words and never contains a stack trace, a path or SQL; the detail goes to the log with the actor, the route or command, and the Job id.

## Build decisions

Settled while building; they refine the sections above, which they replace where they differ.

| Topic             | Decision                                                                                                                                                                                                                                                                                                                                                              |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Order             | The back end is built first (Documents, Results, Jobs, Workflows, CLI), then the editor is moved onto it in one change, so the user interface is rewritten once against the final services. The old registry, edit files and native dialogs are removed in that change.                                                                                               |
| CSRF              | Start's own `createCsrfMiddleware` runs on every request that changes data, as a global request middleware, with the trusted origins from the configuration. There is no separate token: Fetch Metadata, the Origin header and `SameSite` cookies cover browsers.                                                                                                     |
| Errors middleware | Also global (`functionMiddleware`), so a server function that forgets it cannot leak an error. A test requires every `createServerFn` call to list a middleware chain.                                                                                                                                                                                                |
| Changes           | The editor sends one `DocumentChange` at a time (`add-step`, `remove-step`, `move-step`, `set-options`, `set-settings`, `set-enabled`), never a whole Pipeline. The client and the server apply it with the same function.                                                                                                                                            |
| History patches   | An entry stores the forward change and its inverse change. Undo applies the inverse of the entry below the cursor and redo applies the forward change of the entry at the cursor. `history_cursor` is the position the next change takes, and positions never shift, so trimming the oldest entries moves nothing.                                                    |
| Source files      | Deleting a Source removes only its row. Files with no row are removed by a sweep (startup and daily) once older than a grace period, which closes the race between a delete and an upload of the same image. An upload writes its row before keeping the file.                                                                                                        |
| Job claiming      | The DAO offers primitives (`listWaiting`, `countRunningByGroup`, `claim` as one atomic update), and a pure `pickNextJob` holds the fairness rule and is tested alone.                                                                                                                                                                                                 |
| Job liveness      | `claimed_by` names the process and its start time. Running Jobs are failed when their process is gone, checked at startup and every minute by every scheduler, so a server start does not kill Jobs a CLI process is running. Cancelling a running Job sets `cancel_requested`; its worker polls and stops it.                                                        |
| Job completion    | Finishing a Job and enqueueing the Jobs that follow it are one transaction, so a crash cannot lose a workflow run's next segment.                                                                                                                                                                                                                                     |
| Run retention     | A run is kept until the User deletes it, because its Results cascade-delete with it; only Jobs are swept at `JOB_RETENTION_DAYS`. Work images live in `.data/work/run-<id>` and are removed when the run ends, and the daily cleanup removes work folders older than a day.                                                                                           |
| Workflow runs     | A run is one Job per Source per segment. A segment is the Sharp steps between AI steps, or one AI step, and the last segment also encodes the output. Intermediate images are work files that are removed when the run ends. A GPU worker that claims an AI Job also claims waiting Jobs with the same `batchKey`, up to `AI_BATCH_SIZE`, and runs them as one batch. |
| Output settings   | A Workflow's Output keeps format, format options, metadata, widths and suffix. The folder, the "existing files" policy and the manifest are choices for writing a run to disk, so they are flags of the CLI's `workflow run` and `workflow results`, not saved settings: the website has no server path to write to.                                                  |
| Serving images    | A Source is served at `/api/sources/<id>` and a Render at `/api/documents/<id>/renders/<kind>/<key>` (`kind` is `preview` or `thumbnail`), both after the ownership check. A Result is served at `/api/results/<id>`, as a download.                                                                                                                                  |
| Upload            | The body of `POST /api/sources` is the image bytes, with `Content-Type` and `X-File-Name` headers; there is no multipart parsing. The guard checks the declared type against the magic number, the size and the rate, and the service then decodes the file to learn what it really is.                                                                               |

## Testing

Each layer is tested at its own level, and a slice is not done without its tests (written first).

- **Services:** against in-memory fakes of the DAOs and tools. Every ownership rule, every error in "Errors", and every History case (add, remove, move, set, enable, undo, redo, a new change after an undo, the 100-entry cap, a revision conflict) is a test.
- **DAOs:** one shared contract test suite, run against every implementation (the in-memory fake and SQLite now, any later database), so a new database is accepted when it passes the same suite. SQLite tests use an in-memory database with the real migrations.
- **Scheduler and queue:** against a fake clock and fake engines: fairness between two Documents, a workflow run that cannot starve a preview, priority, latest wins, cancel, the restart rule, and two claimants taking different Jobs.
- **Middleware:** each on its own, then the full chain on one route: unauthenticated is 401, a missing CSRF token is rejected, a bad body is 422, an oversized upload is refused before storage, and no response contains a stack trace.
- **CLI:** each command through the real dispatcher with the composition built on in-memory fakes; the JSON output and exit code are asserted.
- **Browser:** the user interface is covered by component tests. Real uploads, a real upscale on a GPU and the pages in a real browser cannot be checked in the sandbox, so each slice lists what it could not check in "Not checked in the sandbox".

## Production bar

Every step is built to its final form. There is no backwards compatibility, no temporary or transitional code, and no legacy code kept alongside the new. When a step replaces something, the old code, its tests, its stored data handling and its documentation are removed in the same change.

- No fallbacks, shims, feature flags, stubs, placeholder UI or "for now" paths. A step ships only the behaviour it fully implements, with every state handled (loading, empty, failed, cancelled, stale) and every failure shown in plain words.
- No migration or compatibility for earlier saved formats. Saved data that no longer matches its schema is reported as unreadable (as a DAO does for a row that fails its schema), never converted.
- Strict TypeScript, schemas as the source of truth, tests written first and kept, accessible and keyboard-operable UI, and nothing that can overwrite saved edits after a failed load.
- A step is done only when `vitest run` exits 0, `tsc --noEmit` and `biome check .` are clean, and this file's "Built" section describes it.

## Goal

Each open Document is a Source plus an ordered **Pipeline of Steps** (Sharp tools and AI tools, Upscale first). The editor shows the result of running the Source through the Pipeline. Steps can be added, edited, reordered, turned off and deleted. This is the same Step model the workflow canvas already uses (`src/features/workflows/workflow-graph.ts`), so a Document's Pipeline can later be saved as a workflow and a workflow can run on one open Document.

This replaced the "version per Apply" model, which has been removed. An AI Step's Job, its progress and Cancel are part of the Pipeline.

## Decisions

| Topic                     | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Model                     | A Pipeline per Document, not a history of rendered versions. Never overwrite the Source.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Sidebar                   | Each open Document is collapsible; expanded, it lists its Steps in order. Drag to reorder, delete, switch a Step off. Selecting a Step opens its options in the Tools panel.                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Tools panel               | Strip keeps three things: Tools (searchable, grouped browser that adds a Step after the selected Step), the selected Step's options, and Export. Export stays separate: it is the output end, not an edit.                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Which tools               | All Sharp tools except the Output group (23 ops: formats, metadata, tiles, timeout), which Export covers. 41 tools: Geometry (9), Filters (18), Colour (13), plus AI Upscale. None dropped. Resizing is the Resize tool in Geometry; Export has no width on purpose.                                                                                                                                                                                                                                                                                                                                                                           |
| Undo/redo                 | History is separate from the Pipeline: reversible patches (see "History patches"). A new change after an undo clears the redo entries. Show original is a view toggle and makes no entry.                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Persistence               | Pipeline and History are saved per Document and survive closing it. Stored in the Document's row, keyed by its permanent id; the Source is stored by content hash, so it can never move or change and there is no "changed Source" state. History is capped at 100 entries.                                                                                                                                                                                                                                                                                                                                                                    |
| Render cache              | A cache, not saved state. On disk under `.data/render-cache/`, keyed by a hash of the Source plus every Step up to that point, so a change re-renders only what the key no longer matches. Capped at 2 GB, least recently used removed first; there is no per-Step cleanup.                                                                                                                                                                                                                                                                                                                                                                    |
| Preview                   | Sharp on the server applies the Steps to the real image and then shrinks the result to at most 2560 px for display, so a pixel size in a Step (extract, resize, blur sigma) means the same in the preview as in the export. Every tool uses the same engine as the export. A downscaled proxy was dropped: it needs every pixel-sized option rescaled, which cannot be done faithfully for tools like convolve or composite. There is no zoom to full size; Export is always full size. WebGPU is deferred: it would only speed up slider scrubbing for a few simple tools and needs a shader per tool. Revisit only if scrubbing feels laggy. |
| Thumbnails                | 48 px in the sidebar, made at 96 px, showing the Pipeline up to that Step. Only for expanded Documents, cached like any Render. A Step that cannot be shown yet (an upscale before it is not rendered, a Step not set up) has none.                                                                                                                                                                                                                                                                                                                                                                                                            |
| Disk use                  | Full-size results of Sharp Steps are not stored; they are recomputed from the Source. AI Step results are kept as Results, never evicted (see "AI tools and Results").                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Apply button              | None for fast (Sharp) Steps: the preview re-renders shortly after each change. AI Steps (Upscale first) keep an explicit Run, because each is a long GPU job. Changing its options marks the Step "out of date", the preview keeps the last Render, and later Steps wait.                                                                                                                                                                                                                                                                                                                                                                      |
| Undo entries              | One entry per committed change. Every edit in an options form is debounced (`use-debounce`, 400 ms) and flushed when a field loses focus or the form closes, so a run of typing or a slider drag is one entry.                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Upscale                   | No longer its own tab. It is a tool under AI in the browser and a Step in the Pipeline. Its sidebar row shows state: rendering with percent and Cancel, out of date, or failed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Tools needing extra input | Composite, Join channel, Boolean (second image), Affine, Recomb, Convolve (matrix), Resize/Extend/Flatten backgrounds and Tint (colour). All included. Needs three new form fields (below). A Step that points at another image stores that Source's id and shows a clear "image not found" state if the Source was deleted.                                                                                                                                                                                                                                                                                                                   |

## Editor build order (all five steps built)

1. Per-Document Pipeline model, saved to the server and restored on open, with its History. Reuse the workflow node schema.
2. Rendering with the cache (Sharp Steps live, Upscale on Run).
3. Sidebar: collapsible Document with its Step list, drag to reorder, off and delete.
4. Tools browser (search, groups) and the option forms for the existing tools, shown for the selected Step.
5. New form fields, then the remaining tools:
   - image chooser (system file dialog, or pick from open Documents);
   - matrix/kernel grid editor;
   - colour picker (CSS string or `{r, g, b, alpha}`).

## What the editor reuses

- Step model, `canConnect`, insert/append/remove helpers: `src/features/workflows/workflow-graph.ts`.
- Option forms generated from the image CLI's schema, with plain-words problems: `sharp-op-fields.ts`, `sharp-option-field.tsx`, `sharp-options-form.tsx`.
- Upscale settings form: `src/features/upscale/`.
- Export formats and per-format fields: `src/features/export/`.
- Segments of a Pipeline or workflow graph: `src/features/workflows/segments.ts`.

## Working rules for this project

Follow the production bar above. Write tests first. Check `vitest run` exit code, not just the pass count (unhandled errors fail the run). Do not commit without being asked.

## Not checked in the sandbox

- **A real upscale.** It needs a GPU with a Vulkan driver; the Upscayl adapter is tested against a fake CLI and a fake engine.
- **The pages in a real browser.** The editor and the workflow page are covered by component tests, not clicked through (upload, drag to reorder, polling, downloads).
- **Server functions over HTTP.** The upload and serving routes and the session, CSRF and rate-limit guards were driven with curl against a dev server; the server functions (documents, render, jobs, results, workflows) are tested through their services and the chain test, not called over HTTP.

# Architecture: processes, database and jobs

Lemonify runs on one machine as a small family of processes that share one Postgres database and one data folder. This note explains how they divide the work and why. The decisions it cites are numbered in [the job workers to-do](job-workers-todo.md); the services, DAOs and job rules themselves are described in [the editor pipeline plan](editor-pipeline-plan.md).

## The processes

The **web server** answers pages, API requests and sign-in, and holds the realtime server that tells open tabs what changed ([live updates](live-updates.md)). It runs no job itself (decision 1, worker processes). When it starts it forks its **worker processes** with `child_process.fork` (`src/server/worker/main.ts`): `LEMONIFY_CPU_WORKERS` CPU workers, each running one Sharp job at a time, and, only while there is AI work, `LEMONIFY_GPU_WORKERS` GPU workers that batch AI jobs (decision 2, pool shape; decision 8, GPU worker start). A **CLI command** (`pnpm images …`) builds the same core in its own process; when it queues jobs it leaves them to the web server's workers if a web server is running, and does them itself if not (decision 6, CLI).

Before this split the web server ran every job in its own process. A render then took the helper threads that file reads, uploads and sign-in need, and the CPU that requests need: with four renders running, reading a tiny file took 1.2 s, and with eight queued, 2.4 s. Moving the work into separate processes gives each its own event loop and its own helper threads, so a busy render can no longer hold up a request. Separate processes are not enough on their own: Sharp uses as many threads as it is given, and when the CPU workers shared every core between them a request still waited 100–230 ms behind a long render. So four cores are kept for the web server (`CORES_KEPT_FOR_WEB_SERVER` in `src/server/config/config.ts`): its main thread and its helper threads, which read files and check sign-ins. The CPU workers share the rest (`imageThreadsPerWorker`), and by default there is one CPU worker per remaining core, at most four. The workers also run ten steps of niceness below the web server (`workerPriority` in `src/server/worker/worker-environment.ts`), so when other programs on the machine want the cores too, the operating system runs the server first. With every CPU worker busy, requests take 30–45 ms and the slowest of ten 50–130 ms.

## Postgres, and why it replaced SQLite

Every process talks to Postgres through Knex and the `pg` driver, each with a pool of its own: `LEMONIFY_DATABASE_POOL_SIZE` (default 10) for the web server and a CLI command, two connections for each worker (`WORKER_DATABASE_POOL_SIZE`), so all of them together stay well inside Postgres's connection limit (decision 9, Postgres). The settings are the required `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DATABASE` and `POSTGRES_SCHEMA`, read from the environment and from `.env` (the environment wins), the same ones `compose.yaml` reads to run Postgres 18 for development (decision 13, local Postgres). Better Auth keeps its own `pg` pool on the same settings, beside the DAOs. Its own rate limiter is turned off: it is on only in production and cannot see a visitor's address, so it would put every visitor in one bucket. The app's guard in front of its routes limits them by each visitor's real address instead.

SQLite was replaced because separate worker processes write to the database often and at the same time, which SQLite handles worst. `better-sqlite3` waits for a lock on the main thread: a write blocked for 2.9 s froze its process's event loop for 2.95 s. The `pg` driver is asynchronous, so waiting for a lock is a pending promise and the event loop goes on serving everything else (decision 5, database waits). No retry layer is built; instead every connection sets `lock_timeout` (5 s) and `statement_timeout` (30 s), so a wait that goes wrong ends with a clear error rather than hanging. A database that cannot be reached is an `unavailable` error (HTTP 503, CLI exit code 7) that names the host and port and how to start the local server.

SQLite also let only one writer in at a time, and three DAO methods relied on it: they read a value, checked it, and wrote the next one. Under Postgres's default isolation two transactions can both pass that read, so an undo and an edit in another tab could both save the same revision, two edits at once could end in a raw key error, and a cancel could be missed while a job finished. Those reads now take the row with `FOR UPDATE` (decision 12, row locks), so the second transaction waits for the first and then sees its result: a stale revision becomes the usual conflict, and a cancel is never missed. Each case has a test that runs two transactions at once (`src/server/dao/postgres/row-locks.test.ts`). JSON columns are `jsonb`, flags are `boolean` and times are `timestamptz` read back as UTC ISO strings, so the DAO interfaces and the services did not change (decision 11, column types).

## The job queue across processes

The queue is the `jobs` table. A worker takes a job with one conditional update, so two processes never take the same one, and fairness (`LEMONIFY_GROUP_SHARE`) is worked out from the table rather than from one process's memory. Work is shared out per job, one per input image or per segment of a run with AI steps, so one workflow spreads over every worker (decision 3, work per image). A job's progress is saved to the database, which tabs and CLI commands read.

The web server's supervisor (`src/server/worker/supervisor.ts`) keeps the pool running. When a job is queued on the website, or another process says it queued one, it tells that pool's ready workers to look for a job at once; otherwise each worker looks every second. It checks the queue for AI jobs every two seconds, starts the GPU workers when one is waiting and stops them after five minutes with none, so no AI models are loaded and no GPU memory is held while nobody uses AI. A worker that stops is started again after 1 s, doubling to 30 s if it keeps stopping, and back to 1 s once it has stayed up a minute. The job a stopped worker was running is failed at once with the usual message ("The program running this job stopped before it finished"), which closes a workflow run's part of it and tells its owner's tabs; every scheduler also checks for such jobs every minute. When the server stops, the supervisor asks each worker to stop, and each finishes the job it is running before it exits; one still busy after two minutes is ended and its job failed. However the server process ends, even when it is killed, its workers see `fork`'s channel close and do the same.

Workers and the supervisor say little to each other, over `fork`'s channel (`src/server/worker/worker-messages.ts`): a worker says `ready` and `stopping`, and the supervisor says `wake`. A worker starts with the web server's database, data folder and worker counts, whatever its environment says, and with a helper thread pool sized for its work (`UV_THREADPOOL_SIZE`).

## The channel between processes

Every process other than the web server reaches it through one local socket, `run/lemonify.sock` in the data folder (decision 4, live updates). A process writes one JSON line per message: a `change`, the same event a person's tabs are sent, which names what changed and never its content (decision 7, CLI and website), or `queued`, the pools it queued jobs for, so their workers start on them now. The web server checks every line against a Zod schema and logs and drops what fails it. Sending never waits and never fails a command: with no web server running the connection fails at once and the message is dropped.

The socket's folder is created with mode 0700 and must belong to the user who runs Lemonify, and the socket itself is 0600, so only that user's processes can reach it. That the socket answers is how a CLI command knows a web server is running (`webServerAnswers`); a socket left by a killed server does not answer, and a second web server on the same data folder is refused, since the two would split the changes between them.

## The CLI

A CLI command builds the same services from the same composition (`createApp`), so it behaves exactly like the website. When it queues jobs and waits for them (`export`, `workflow run --follow`, `--preview` and the rest), it first asks whether a web server is running (`scripts/images/job-workers.ts`). If one is, the command queues the jobs, says so through the socket and waits for their results, so however many people or agents run commands at once, no more jobs run than the pool allows. If none is, or the one that was stops while the command waits (it checks every two seconds), the command takes the jobs from the queue itself with the same pools and fairness rules, so the CLI still works on its own. The `worker` command runs that scheduler until it is stopped, for doing queued work when no web server is running.

## Testing

DAO tests and the end-to-end run use a real Postgres, because the row-lock tests need two connections (decision 14, test databases). Each test run migrates one template database, and every test that needs a database gets its own copy and drops it at the end, so tests stay isolated and files run in parallel; Vitest points `POSTGRES_DATABASE` at a database that does not exist, so a test that forgets to make its own fails instead of touching the database in `.env`. Tests that start processes of their own (worker processes, CLI commands, a web server's pool) are named `*.process.test.ts` and run as a separate Vitest group after the rest, so the processes they start do not take the CPU from tests with short timeouts. The end-to-end run builds the app and tests the built server (`vite preview`), because that is what ships: it found two faults the development server hid, a file the build did not carry (now imported, and `src/lib/build-safety.test.ts` keeps any module from reading files beside itself) and Better Auth's own rate limiter, which is on only in production. `e2e/responsiveness.spec.ts` checks that the web server answers within 100 ms while a document row is locked, and within 250 ms (the slowest of ten requests) while the CPU workers are busy with long renders; a server that ran the renders itself took 400–2300 ms.
